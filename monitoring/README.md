# Monitoring and observability for TaskBoard Lite

**Student:** Vivek Singh Solanki | **Roll number:** 24bcs10338

Three signals are covered: **metrics** (Prometheus + Grafana), **logs**
(structured stdout collected by Docker / kubelet) and **alerts** (Prometheus
alerting rules). The same metrics and rules work in the docker compose stack
and in Kubernetes with kube-prometheus-stack; only the discovery mechanism
differs.

## Metrics

The application exposes `GET /metrics` in the Prometheus text format using
`prometheus_client`:

| Metric | Type | Labels | Meaning |
|---|---|---|---|
| `taskboard_requests_total` | counter | `endpoint`, `method`, `status` | every HTTP request, labelled with the Flask route rule (bounded cardinality: `/api/tasks/<int:task_id>` rather than `/api/tasks/42`) |
| `taskboard_tasks_created_total` | counter | - | tasks created since the process started |
| `taskboard_tasks_open` | gauge | - | tasks not marked done; refreshed on every scrape and after every write |
| `up` | gauge | `job`, `instance` | generated by Prometheus: 1 when the scrape succeeded |

Note on gunicorn: the image runs 2 worker processes and each one has its own
registry, so counters are per-worker (each scrape hits one of them). The gauge
is refreshed from SQLite on every scrape, so it is always consistent. A
production setup would enable `prometheus_client` multiprocess mode or run a
single worker per pod and scale with replicas (which is what the HPA does).

### docker compose (`docker/docker-compose.yml`)

```bash
cd docker && mkdir -p data && chmod 777 data && docker compose up --build
```

- `prometheus.yml` scrapes `prometheus:9090` (itself) and the job `taskboard`
  at `app:8000/metrics` every 15 s, and loads `alerts.yml`.
- Grafana starts with anonymous admin access, the Prometheus datasource
  (`grafana/provisioning/datasources/datasource.yml`) and the dashboard
  (`grafana/provisioning/dashboards/taskboard.json`) already provisioned.

| URL | What to look at |
|---|---|
| http://localhost:9090/targets | both targets `UP` |
| http://localhost:9090/alerts | the four rules, state `Inactive` |
| http://localhost:9090/graph?g0.expr=taskboard_tasks_open | raw metric |
| http://localhost:3000/d/taskboard-lite | dashboard: target status, open tasks gauge, 5xx ratio, tasks created, request rate by endpoint, responses by status |

Generate some traffic to see the panels move:

```bash
for i in $(seq 1 20); do curl -s -X POST -H 'Content-Type: application/json' -d "{\"title\":\"task $i\"}" localhost:8000/api/tasks > /dev/null; done
for i in $(seq 1 50); do curl -s localhost:8000/api/tasks > /dev/null; curl -s localhost:8000/api/tasks/9999 > /dev/null; done
```

### Kubernetes (kube-prometheus-stack)

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm upgrade --install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace
kubectl apply -f monitoring/servicemonitor.yaml -f monitoring/prometheus-rules.yaml
kubectl -n monitoring port-forward svc/kube-prometheus-stack-prometheus 9090:9090
kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80   # admin / prom-operator
```

- `servicemonitor.yaml` tells the operator to scrape every Service labelled
  `app.kubernetes.io/name: taskboard-lite` in namespace `taskboard` on the
  port named `http`, path `/metrics`. Both the plain manifests and the Helm
  chart name the Service port `http`.
- `prometheus-rules.yaml` carries the same four alerts as `alerts.yml`. The
  job label is `taskboard-lite` there (the operator names jobs after the
  Service), which is the only difference between the two files.
- The dashboard JSON can be imported into the stack's Grafana as is
  (Dashboards -> New -> Import) after selecting its Prometheus datasource.

## Logs

The app logs to stdout with the level from `LOG_LEVEL`
(`2026-10-07 10:00:00,000 INFO taskboard-lite: task created id=3`). It never
logs `DB_PASSWORD`; it only logs whether the variable is set.

```bash
docker compose logs -f app                                   # compose
kubectl -n taskboard logs deployment/taskboard-lite -f       # kubernetes, all pods of the deployment
kubectl -n taskboard logs -l app.kubernetes.io/name=taskboard-lite --tail=50 --prefix
```

`LOG_LEVEL` lives in the ConfigMap, so switching to `DEBUG` is a config change
plus a rollout, not a code change. In a larger setup the same stdout stream is
shipped by Loki / Fluent Bit / CloudWatch; nothing in the app would change.

## Alerts

| Alert | Expression (short) | For | Severity | Why |
|---|---|---|---|---|
| `TaskboardDown` | `up{job="taskboard"} == 0` | 1m | critical | the scrape fails: pod gone, port wrong, network policy |
| `TaskboardHighErrorRate` | 5xx share of all requests > 5% | 2m | warning | app is up but failing requests |
| `TaskboardNotReady` | `/ready` answering 503 | 2m | warning | database directory not writable (volume permissions) |
| `TaskboardHighCpu` | cAdvisor CPU > 0.15 cores per pod | 5m | warning | rule for the Kubernetes deployment (uses cAdvisor metrics from kube-prometheus-stack) |

Try it: `docker compose stop app`, wait a minute, open
http://localhost:9090/alerts and `TaskboardDown` goes `Pending` -> `Firing`.
Alertmanager routing (Slack, email) is out of scope; the rules are the part
that is identical in every environment.
